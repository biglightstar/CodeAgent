# 前端视觉质量评审流程

## 前置条件

1. 确认开发服务器已经启动，并从进程或任务结果中获取实际本地访问地址。
2. 如果已经配置浏览器 MCP Server（如 Playwright MCP），使用它打开准确的本地地址并获取截图；视觉判断必须基于实际截图，而不是仅凭 HTML/CSS 源码推断页面观感。
3. 打开页面后，在截图前确认：
   - 页面是否已经真正加载完成，而不是处于加载中状态。
   - 是否出现加载失败、404 或明显的错误页面。
   - 如果页面依赖测试数据或需要登录，是否已准备好必要的测试数据、是否停留在正确的页面上。
   - 是否存在遮挡主要内容的弹窗、提示条或加载动画。
   - 截图本身是否完整（没有被截断或空白）。
   不满足以上条件时视为截图无效，不能将页面未加载完成的状态当作设计缺陷来评审。
4. 如果没有可用的浏览器工具，或视觉分析不可用，必须明确说明无法进行真实视觉检查，不能假装已经查看过截图或伪称视觉评审已经完成。

## 评审维度

每轮评审依次检查以下六个维度，并在桌面、平板、手机三档视口下分别执行（视口尺寸为建议值，不是所有项目必须采用的固定断点，可结合 responsive-design 的断点规则调整）：

| 设备 | 建议视口 | 本维度检查重点 |
| --- | --- | --- |
| 桌面端 | 1440 × 900 | 整体布局、内容宽度、视觉层次 |
| 平板端 | 768 × 1024 | 导航变化、栅格调整、内容排列 |
| 手机端 | 375 × 812 | 单列布局、文字换行、触控操作 |

1. **视觉主题**：页面是否具有明确、统一的设计风格，是否与 frontend-design 阶段确定的视觉方向一致，而不是多种风格混杂。
2. **布局质量**：信息层级是否清晰，首屏视觉焦点是否明确，留白是否合理，对齐方式和整体视觉节奏是否协调。
3. **色彩排版**：配色是否统一协调，文字与背景/组件表面是否有足够对比度，字体层级（标题/正文/辅助文字）是否清晰，行长和可读性是否合适。
4. **素材质量**：图片裁切、宽高比例和内容相关性是否合理，图标是否统一且非 Emoji 代用，是否存在无意义占位素材。
5. **交互体验**：按钮、导航、表单控件的可辨识度和反馈是否正常，键盘焦点状态是否可见，是否存在明显的可用性障碍。
6. **响应式**：在三档视口下分别检查是否存在内容溢出、元素裁切或布局错乱；如果浏览器工具能够提供控制台信息，检查是否存在运行时错误。

### 问题分类

发现的问题必须归入以下三类之一，不同类别的修复方式不同，不能混为一谈：

- **视觉问题**：颜色、排版、留白、布局、图片、视觉层级等观感问题，修复方式是调整样式和设计 Token，不涉及业务逻辑。
- **功能问题**：按钮无响应、链接错误、表单提交失败、弹窗无法关闭等行为缺陷，修复方式是修正交互逻辑，不能靠调整样式掩盖。
- **响应式问题**：特定视口下的元素溢出、布局错乱、内容裁切，修复方式是调整该视口下的布局结构。

不得为了修复视觉问题而顺手修改原本正常的业务逻辑，也不得把功能问题当成视觉问题用样式掩盖（例如用 `overflow: hidden` 掩盖提交失败后的错误信息）。

区分客观缺陷（布局错乱、对比度不足、溢出、功能障碍）和主观设计偏好，优先修复阻碍使用或明显破坏视觉/布局的问题。

## 截图覆盖范围

单张首屏截图不足以发现页面的全部问题。每轮评审至少覆盖：

- 页面首屏。
- 页面中部的主要内容区域。
- 页面底部。
- 页面较长时，必要时对整页进行完整截图（或分段截图拼接检查）。
- 导航菜单展开态、弹窗、下拉框等默认不可见的重要交互状态，需要触发后单独截图检查，不能只看页面的静态初始状态。

## 问题描述格式

每个发现的问题必须包含以下字段，不能给出「页面不够美观」「布局不够协调」这类无法指导修改的模糊结论：

| 字段 | 说明 |
| --- | --- |
| 位置 | 页面哪个区域（如「首页 Hero 区域」「手机端导航」） |
| 分类 | 视觉 / 功能 / 响应式 |
| 具体表现 | 截图中实际观察到的现象 |
| 影响 | 为什么影响视觉效果或使用体验 |
| 修改建议 | 应该调整什么（具体到元素或设计 Token，而不是泛泛而谈） |
| 优先级 | 高 / 中 / 低 |

## 评审报告

每轮评审结束后输出一份结构化报告，而不是直接开始修改：

```
Frontend Review Report
评审轮次：第 N 轮

本轮检查范围：
- 截图覆盖（首屏 / 内容区 / 底部 / 关键交互态）
- 视口（桌面端 / 平板端 / 手机端）

发现的问题：
（按问题描述格式列出，按优先级排序）

本轮修复计划：
1. ...
2. ...

验证结果：
待修复后重新截图验证，不提前宣称问题已解决。
```

## 迭代流程

1. 每轮基于评审报告中的问题列表，选出当前最重要的三个问题，按优先级排序。
2. 修改前先记录本轮要解决的问题及涉及的文件范围。优先修复排序最靠前、最明显的缺陷，每轮只进行一组范围明确、彼此相关的修改；禁止为了修复局部视觉问题而大范围重写页面、替换技术栈或修改无关组件。
3. 具体代码修改交由 frontend-development 执行（见「与其他 Skill 的协作」），frontend-review 自身负责发现问题、形成修复任务和验证结果。
4. 修改后重新截图，与修改前的截图逐项对比，确认原问题是否改善，是否引入新问题，并更新评审报告的「验证结果」部分。
5. 满足以下任一条件时停止自动迭代：
   - 本轮没有发现新的客观缺陷。
   - 剩余问题均属于主观设计偏好，交由用户决定是否调整。
   - 浏览器工具或视觉分析出现故障，无法继续获取有效截图。
   - 连续两轮修改后同一问题没有改善。
   - 达到最大迭代轮次（建议不超过 3-4 轮）。
   停止后汇报仍然存在的问题、已尝试的修改和建议，交由用户决定是否继续。
6. 只有浏览器截图证据能够支持结论时，才能声称某项视觉要求已经通过；不能仅凭代码审查断言视觉效果达标。

## 截图处理规则

当浏览器 MCP 工具返回截图图片内容时，MCP 适配层会自动将图片作为原生 `input_image` 内容转发给已配置的、支持视觉输入的 Responses 模型。阅读工具结果中包含的视觉分析，对照评审维度和问题分类整理出具体问题，按问题描述格式记录，然后再次截图验证。

执行截图分析前，必须确认图片内容确实到达了视觉模型，而不是想当然地认为流程生效：

- 如果 MCP 返回的只是图片路径、文件名、Base64 元数据或纯文本描述，而工具结果中没有看到实际传递图片内容给视觉模型并返回的分析文本，则不得将其视为完成了视觉分析。
- 如果工具结果不包含图片，或报告了视觉分析错误、超时、格式不支持等问题，必须明确说明基于截图的检查没有完成，本轮视觉评审结论无效；不能假装已经检查过截图，也不能用源码推断代替视觉分析后假称已完成截图检查。

## 与其他 Skill 的协作

- frontend-review 不负责设计决策和具体实现，也不应该自己直接改动代码：它负责发现问题、按问题描述格式和优先级形成修复任务，写入评审报告。
- 修复任务交由 frontend-development 实施：视觉问题和响应式问题分别对照 frontend-design 的设计规范、responsive-design 的布局规则修复，功能问题按预期交互行为修复。
- frontend-review 是视觉迭代闭环中的检查环节：实现 → 评审 → 修复 → 再评审，直至问题收敛、触发停止条件或达到迭代轮次上限。
