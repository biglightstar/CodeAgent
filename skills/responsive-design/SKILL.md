# 响应式设计检查

## 基本原则

1. 调整断点之前，先确定页面内容的优先级，明确不同屏幕尺寸下哪些内容最重要、哪些可以折叠或延后展示。
2. 优先使用流式宽度和弹性布局能力（flex、grid、相对单位），再考虑增加固定像素宽度；不要依赖大量固定尺寸拼凑响应式效果。
3. 不同屏幕下应重新组织布局结构（例如多列变单列、侧边栏折叠为抽屉或汉堡菜单、卡片网格改变列数），而不是把桌面端布局整体等比缩小字体和元素。

### 断点选择原则

测试视口和 CSS 断点是两个不同的概念，不能混为一谈：三档视口（见下）是必须覆盖的测试范围，不代表项目只能定义三个 CSS 断点。断点应根据页面内容和布局实际发生变化的需求确定，而不是机械套用固定设备型号的宽度。具体做法是观察当前布局从哪个宽度开始出现拥挤、换行异常或空间不足，在该位置设置断点；不同页面、不同组件的断点可以不同，不必强行统一成一套通用断点。

## 三档视口检查

至少覆盖以下三类视口，不能只检查桌面端和手机两端而跳过平板：

- 桌面端（约 1280px 及以上）
- 平板端（约 768px–1024px）
- 手机端（约 375px–428px 窄屏）

针对每个视口逐项检查：

1. 导航栏：能否合理折叠（如收纳为汉堡菜单），窄屏下是否仍可完整访问所有导航项。
2. 图片：裁切和宽高比例是否合适，是否按容器宽度自适应，是否存在变形或溢出。
3. 卡片/内容块：是否正确换行堆叠，窄屏下是否仍保持合理的内边距和间距，而不是紧贴边缘。
4. 表单：输入控件宽度是否合理，标签和控件是否对齐，窄屏下是否仍方便填写。
5. 文字：字号在窄屏下是否依然可读，行长是否合适，是否出现文字溢出容器或被截断。
6. 触控区域：按钮、链接、表单控件等可点击元素在手机端的尺寸是否足够点击，相邻可点击元素间距是否足够避免误触。
7. 横向溢出：确保页面内容在各个视口下都不会产生不必要的横向滚动。

### 特殊组件适配

以下组件在普通内容区域检查之外容易单独出问题，应根据实际使用场景制定适配方式，不能遗漏：

- 数据表格：窄屏下是否需要横向滚动容器，或改为卡片化展示。
- 侧边栏：是否需要折叠或转换为抽屉。
- 弹窗：尺寸和位置是否会在手机屏幕下超出可视区域。
- 下拉菜单：展开后是否被视口边缘裁切。
- 固定定位的底部操作栏/悬浮按钮：是否遮挡下方页面内容。
- 长文本和代码块：是否会导致容器横向溢出或破坏布局。

### 横竖屏与极端内容检查

- 在适用场景下（例如移动端优先的页面），检查设备横屏与竖屏之间的布局变化是否都正常。
- 测试时不能只用短标题和少量示例数据：应额外用长标题、超长单词（如长链接、长邮箱地址）、较长用户名、内容为空、数据量较大等极端情况验证，避免示例数据下表现正常、真实数据下出现布局错乱。

## 信息层级一致性

窄屏适配不等于简单等比缩小桌面端设计。在适配过程中：

- 保留桌面端确定的视觉重点和操作优先级，核心操作入口不能在窄屏下被埋没或移出首屏。
- 允许根据屏幕尺寸重新排布甚至隐藏次要内容，但不能打乱页面的信息层级逻辑。
- 移动端页面应当独立具有清晰的视觉焦点，而不是桌面端布局的缩小版。

### 响应式视觉一致性

响应式调整不能破坏 frontend-design 阶段确定的视觉系统。不同视口下可以改变布局结构、元素尺寸和排列方式，但颜色体系、字体层级、组件风格和整体视觉方向必须保持一致。不能为了适配手机端而随意创建另一套互不相关的视觉规范，导致桌面端和移动端看起来像两个不同的产品。

## 验证方式

- 如果浏览器工具（Playwright MCP）可用，必须实际在上述三档视口中分别打开页面验证，而不是仅凭 CSS 代码推断效果。
- 如果没有可用的浏览器工具，必须明确说明响应式验证基于代码审查而非实际渲染结果，不能声称已经在浏览器中验证过。

## 与其他 Skill 的协作

- 响应式断点和布局规则应与 frontend-design 阶段确定的设计系统保持一致，不单独发明新的间距或字体规则。
- 响应式问题的修复在 frontend-development 阶段实现。
- 最终的真实浏览器截图验证和视觉评分由 frontend-review 统一执行，responsive-design 的三档视口检查是 frontend-review「响应式」评审维度的具体执行标准。
