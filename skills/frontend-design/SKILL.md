# 前端视觉设计流程

## 一、需求分析（编码前必须完成）

在选择视觉方向和编写代码之前，先明确：

1. 网站/页面的定位和目标用户：这是什么类型的产品，谁会使用它，用户抱着什么预期打开这个页面。
2. 页面需要解决的问题：用户访问这个页面想完成什么任务，不做无关假设。
3. 核心内容和主要操作：页面必须呈现哪些内容是不可省略的，用户最重要的一个操作入口是什么。
4. 页面类型和内容层级：这是营销落地页、后台管理页、电商详情页、作品展示页还是工具类页面；不同类型的信息层级和密度不同，不能套用同一套结构。

在选择框架或替换文件之前，先检查现有项目。除非用户明确要求，否则保留项目当前使用的框架、脚本、路由和代码约定。

## 二、视觉方向选择

根据需求分析的结论，从以下方向中选择最贴合项目的一种，或明确组合使用：

- Minimalist：内容为主，弱化装饰，依赖留白和排版层级。
- Editorial：强排版、大标题，类似杂志/博客的阅读节奏。
- Bento Grid：用不同尺寸的信息块拼接展示多个并列内容或功能。
- Modern SaaS：产品介绍 + 功能展示 + 转化路径的营销站结构。
- Dashboard：数据密集，以表格、图表、状态信息为中心的管理界面。
- E-commerce：以商品展示、筛选、对比和购买路径为核心。
- Portfolio：以作品或案例展示为核心的个人/机构主页。

选择依据必须来自第一步的需求分析，不要机械套用列表。如果项目类型不属于以上任何一种，可以说明理由后自行定义方向。

**禁止**：不论项目类型如何，都默认套用同一套「导航栏 + Hero 区域 + 三列卡片 + 渐变背景」的组合。如果这套结构确实适合当前项目，必须在设计说明中给出具体理由，而不是作为默认选择。

### 设计灵感与参考分析

确定视觉方向只是定了大致风格，同一个方向（例如 Modern SaaS）在不同产品中可能是极简留白、深色强对比，也可能是大字排版配不对称布局，最终效果差异很大。因此在进入设计系统之前，还需要结合项目类型，具体分析优秀网站或成熟产品的设计特点：

- 重点观察参考对象的布局结构、排版方式、色彩搭配、视觉层次和交互细节，用于提炼可迁移的设计规律，而不是直接照搬某个页面的具体实现。
- 如果已配置网页搜索或浏览器工具，可以主动查找相关设计参考；如果没有可用工具，则基于已有设计知识独立完成设计判断，不得虚构或假称已经查看过具体参考网站。
- 最终产出的设计方向应说明参考了哪类产品的哪些特点（例如「参考同类工具型产品的深色信息密集布局」），而不是只给出一个风格名称。

## 三、建立设计系统

确定视觉方向后，在大面积编码之前，明确以下设计规范，并落实为项目中可复用的样式变量（CSS 变量、主题配置文件、设计 Token 等，具体形式依据项目技术栈而定）：

1. 色彩体系：主色、辅助色、背景色（含层次，例如页面背景与卡片表面的区分）、文字色（主要/次要/弱化）、状态色（成功/警告/错误/信息）。
2. 字体体系：字体族、字号阶梯、字重、行高，并明确标题、正文、辅助文字各自使用的层级。
3. 间距体系：统一的间距尺度（例如以 4px 或 8px 为基准的倍数关系），避免同类元素使用互不一致的随意间距值。
4. 布局体系：内容最大宽度、栅格列数、响应式容器规则、对齐方式。
5. 组件规范：按钮（含默认/悬停/禁用等状态）、导航栏、卡片、表单控件等的统一样式规则。
6. 视觉效果：边框样式、圆角大小、阴影层级、动效时长与缓动方式，且同类元素必须统一使用，不能各自为政。

设计规范必须统一，不能让不同组件各自决定颜色、圆角或间距。

frontend-development 开始实现前，必须读取本阶段产出的设计方案（见「设计输出」一节）。实现过程中优先复用已有 CSS 变量、主题配置和组件样式，禁止在没有设计理由的情况下随意修改颜色、字体、间距、圆角和阴影。如果实现过程中确实需要调整设计规范（例如发现某个取值在真实内容下不成立），应同步更新设计系统的取值或文档，保证整个项目视觉规范的一致性，不允许实现阶段悄悄分叉出第二套规范。

## 四、页面布局设计

对页面的每个主要区域，明确：

- 该区域承担的信息层级和视觉重点（用户在这个区域第一眼应该看到什么）。
- 具体的布局结构，而不是「从上到下排列标题、文字、卡片」这类笼统描述。

特别关注首屏：首屏必须有清晰的视觉焦点和一个最重要的操作入口，不能只是把标题、说明文字和卡片按顺序堆叠展示。

## 五、页面细节设计

整体布局之外，视觉质量也体现在细节上。应根据页面实际需要确定：

- 导航栏滚动时是否需要变化（如背景色渐显、阴影出现、收起为紧凑状态）。
- 按钮、链接等交互元素在悬停、聚焦、按下时是否有清晰反馈。
- 图片的裁切方式、圆角和展示形式（如平铺、卡片式、沉浸式大图）。
- 内容区域之间是否需要分隔线、背景色块或间距来划分层级。
- 页面滚动、区域切换时是否需要合理的过渡效果。
- 内容的重要程度是否通过字体大小、字重、颜色和留白体现出来，而不是所有内容视觉权重相同。

这些细节必须服务于实际内容和功能，不能为了制造效果而堆砌动画和装饰；没有明确理由的细节处理可以从简，不必每个页面都做满。

## 六、素材质量

- 合理使用真实图片、插画和图标，优先选择与业务内容相关的视觉素材。
- 不允许使用 Emoji 代替正式界面图标；界面图标应使用图标库或 SVG。
- 不得为了填充页面随意插入无意义的占位图片；如果暂时没有真实素材，应使用语义清晰、风格统一的占位方案，并明确说明这是占位内容。

## 七、设计输出

无论项目规模大小，设计阶段结束时都必须明确给出以下内容（中大型项目写成独立设计方案文档，简单页面可以直接作为实现前的内部结论，但同样不能缺项）：

| 设计内容 | 需要明确的内容 |
| --- | --- |
| 设计定位 | 页面类型、目标用户、视觉方向（含参考分析结论） |
| 色彩规范 | 主色、辅助色、背景色层次、文字色、状态色 |
| 字体规范 | 字体族、字号阶梯、字重、行高 |
| 布局规范 | 内容最大宽度、区域划分、栅格结构、对齐方式 |
| 组件规范 | 按钮、导航、表单、卡片等各状态的统一样式 |
| 视觉规范 | 圆角、边框、阴影、动效 |
| 页面结构 | 每个区域的具体布局、信息层级和视觉重点 |

- 中大型项目（多页面、具备完整信息架构的项目）：在开发前写出明确的设计方案（对照上表逐项给出取值和理由），并将可复用的设计规范落实到项目样式文件中（如全局样式表、主题变量文件），供 frontend-development 阶段直接引用。
- 简单页面（单页、小范围改动）：不需要为了流程创建大量文档，但仍需在开始实现前对上表的每一项给出明确取值（配色、字体、间距等核心规范不能跳过），避免设计停留在脑海中、开发阶段各自发挥。

## 质量要求

- 页面应当体现经过思考的视觉设计，而不是未经调整的脚手架默认模板。
- 间距和字体使用应保持一致，不同组件不能各自定义独立的视觉规则。
- 交互控件应容易辨认，并支持键盘访问。
- 优先保证布局和内容质量，不要依赖过度装饰制造视觉效果。
- 在适用的情况下，统一处理加载、空数据、错误和焦点状态。
- 完成设计并进入实现后，如果已配置浏览器工具，交由 frontend-review 进行实际检查；只有实际运行了浏览器检查，才能声称已经进行视觉检查。

## 与其他 Skill 的协作

frontend-design 只负责设计决策和设计规范的产出，不负责编码实现、响应式细节适配和最终视觉验收：

- 设计规范确定后，交由 frontend-development 按规范实现。
- 多尺寸适配细节由 responsive-design 负责。
- 实现完成后的真实浏览器视觉检查由 frontend-review 负责。

涉及完整网页开发任务时，这四个 Skill 应按顺序组合使用，不要只调用 frontend-design 就直接开始编码，也不要跳过设计阶段直接进入评审。
