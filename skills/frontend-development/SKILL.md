# 前端开发流程

1. 修改之前先检查项目目录结构，并阅读项目的包管理元数据文件。
2. 确认项目使用的框架、包管理器、脚本命令、现有组件模式和样式组织方式。
3. 如果存在 frontend-design 阶段产出的设计方案或设计规范（设计说明文档、主题变量文件、样式 Token），开发前先完整阅读；没有独立文档时，检查项目现有样式文件中是否已经存在设计规范。
4. 优先遵循项目已有的约定。没有充分理由时，不要替换框架，也不要重写与当前需求无关的文件。
5. 将页面拆分为职责清晰的内容区域，并在确有复用需求时提取组件。
6. 保持数据、展示和交互逻辑之间的职责清晰，便于理解和维护。
7. 使用语义化 HTML 和可访问的标签。交互元素必须使用真正的按钮、链接或表单控件，不要用普通文本伪装成可交互元素。
8. 根据实际情况处理空值、加载状态、错误和基础输入校验。
9. 如果项目提供了代码检查、类型检查、测试和构建脚本，就运行现有脚本；无法运行的命令必须明确说明。运行后重点关注：
   - 是否存在控制台错误和明显的运行时异常。
   - 是否存在未使用的变量、组件或无效代码。
   - 是否存在重复样式和不必要的组件。
   - 是否存在明显的布局溢出和交互失效。
   - 是否存在影响键盘操作和可访问性的实现问题。
   只修复本次修改引入的问题，不要借机重构无关代码；真实的视觉验收仍交给 frontend-review，开发阶段不需要重复承担完整的视觉评审工作。
10. 只有确实需要时才启动开发服务器。将服务器作为受管理的后台任务运行，并在服务就绪后报告本地访问地址。

## 设计实现约束

实现阶段必须忠实执行 frontend-design 确定的设计规范，而不是在编码时重新发明视觉样式：

1. 颜色、字体、间距、圆角、阴影等视觉属性必须使用设计规范中定义的变量或取值，不得在组件中硬编码与规范不一致的数值。
2. 开发前先检查全局样式文件、主题配置和已有组件，确认设计 Token（如 `--color-primary`、`--spacing-lg`、`--radius-md` 等变量）的定义位置。优先复用已有变量，不重复创建同义变量；新增 Token 时应放在统一的主题或全局样式文件中，而不是分散定义在各个组件内部。
3. 对于设计规范没有覆盖的特殊视觉需求，先判断能否用现有 Token 组合实现；确实需要新增取值时，保持与现有设计系统一致（例如新色值需落在既有色彩层级逻辑中，不能脱离整体配色体系）。
4. 同类组件（按钮、卡片、表单控件等）在整个页面或项目中保持统一的视觉风格，不允许不同区域各自发明样式。
5. 避免用大量重复卡片堆叠内容、无意义的渐变背景和纯装饰性元素填充页面；每个视觉元素都应服务于内容表达。
6. 合理使用图标库（优先项目已引入的图标库）或 SVG 图标，不使用 Emoji 代替界面图标。图片素材应与内容相关，不随意使用无意义占位图。
7. 页面内容必须真实、完整，不使用大量「示例文字」或 Lorem ipsum 式的空洞占位文字；确需占位时应使用贴近实际场景的内容，并说明这是占位。
8. 不得为了实现某个视觉效果而破坏现有功能、可访问性或既有交互逻辑。
9. 样式应有合理的作用范围，并与项目现有的样式体系保持一致。

### 设计规范缺失时的处理机制

如果当前任务需要完整的视觉设计，但既没有找到 frontend-design 的设计产出，项目中也不存在已有的设计规范：

1. 暂停正式页面编码，不要凭感觉直接定义颜色、字体和间距。
2. 先调用 frontend-design 完成需求分析、视觉方向选择和基础设计系统建立。
3. 将设计决策落实为可供开发阶段读取的设计规范（变量、文档或项目样式文件）。
4. 完成后再进入本 Skill 的开发流程。

如果只是对已有页面做不涉及视觉调整的小范围功能修改，可以沿用项目现有样式规范，不必为此重新执行完整的设计流程。

## 交互功能完整性要求

页面不能只有视觉外壳。对页面中的每个交互控件，明确其预期行为并完成对应的功能实现：

- 按钮：明确点击后实际执行的操作，不能仅做出可点击的视觉样式却没有行为。
- 链接：具有正确的跳转目标（页内锚点、路由或外部地址）。
- 表单：具备输入处理、必要的校验规则和提交后的反馈（成功、失败、加载状态）。
- 搜索和筛选：操作结果能实际影响页面展示的内容，而不是摆设控件。
- 弹窗、下拉菜单、导航：能够正确打开、关闭，并正常响应点击外部关闭、键盘操作等常见交互。

不得仅为了展示效果添加没有实际行为的交互控件。对于暂时无法接入真实后端的功能，应使用明确的模拟数据实现交互逻辑，并在交付说明中标注这是模拟数据或当前的功能边界，不能含糊其辞。

## 响应式实现约束

页面实现时必须考虑不同屏幕尺寸下的布局变化，响应式不是最后把桌面页面整体缩小：

- 优先使用弹性布局（flex、grid）、相对单位和合理的容器约束，避免依赖大量固定像素宽度造成溢出。
- 如果任务涉及响应式设计，应结合 responsive-design 确定的断点和布局规则进行实现，保证导航、内容区域、图片、表格、表单和交互控件在桌面、平板、手机等不同尺寸下都具有合理的布局结构。
- 不得简单通过整体缩小字体和元素尺寸来实现移动端适配；必要时应调整布局结构本身（如列数变化、折叠、堆叠顺序）。

## 安全与修改纪律

- 只需小范围修改时，绝不能整份覆盖项目配置文件。
- 不得删除用户数据或与当前需求无关的文件。
- Agent 请求执行会修改系统或项目状态的 Shell/MCP 操作时，必须经过全局人工审批。
- 修改完成后，说明改动了哪些文件，以及实际执行了哪些测试和检查、结果如何。

## 与其他 Skill 的协作

- 实现前应已有 frontend-design 产出的设计规范；如没有找到设计产出且当前任务需要完整视觉设计，先按「设计规范缺失时的处理机制」调用 frontend-design，再开始实现。
- 如页面涉及多尺寸适配，参考 responsive-design 的断点和布局要求同步实现，不单独发明响应式规则。
- 实现完成后，交由 frontend-review 使用浏览器工具进行真实视觉检查，不要自行断言视觉效果已经达标。
